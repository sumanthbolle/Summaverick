Dynatrace Davis to ServiceNow HLA: Translating PurePath Anomaly Detection to CMDB-Correlated Log Streams

Beginner · 14 min read · Feb 2026

The Scenario

You've mastered Dynatrace's Davis AI, tracing PurePaths through microservices with causal correlations that make SREs weep with joy. Now your org rolls out ServiceNow Health Log Analytics (HLA), streaming raw logs into CMDB-mapped anomaly detection, and leadership expects you to bridge the gap without missing a beat on MTTR. The ask: translate your event correlation wizardry to ServiceNow's Event Management + HLA stack, where logs become predictive alerts before incidents explode.

Key Questions Answered

Q: What's the ServiceNow equivalent of Dynatrace's core features?

A: Dynatrace Davis unsupervised anomaly detection maps directly to HLA's real-time ML on streaming logs, converting anomalies to CI-correlated events in em_event table. PurePath distributed tracing becomes Service Mapping's top-down service topology + bottom-up log attachment; Smartscape entity relationships = CMDB CI relationships with log enrichment. Alerting intelligence (problem auto-grouping) parallels Event Management's alert correlation rules + HLA's anomaly grouping, but HLA adds genAI Now Assist for summarization and probable cause. Trade-off: Dynatrace's full-stack auto-instrumentation vs HLA's log-focused streaming requiring MID Server proxies or direct Glide log ingestion.

Q: How do integration patterns differ between platforms?

A: Dynatrace OneAgent pushes metrics/logs/traces via ActiveGate; ServiceNow HLA pulls via MID Server proxies or direct integrations (e.g., Systems Log Retriever for platform self-logs, no agents needed). Dynatrace favors agentless HTTP beacons; HLA mandates structured log streaming with parsing/normalization scripts in JavaScript for custom fields. Production insight: Scale HLA with dedicated MID herds per cluster (tame the herd pattern), unlike Dynatrace's cluster-wide ActiveGate; correlation differs as HLA leans on CMDB for topology vs Dynatrace's runtime dependency auto-discovery.

Q: What root cause analysis knowledge transfers directly?

A: Event correlation topologies transfer seamlessly: Dynatrace problem root cause % maps to HLA anomaly ranking + Now Assist genAI probable cause summaries. Anomaly detection baselines (your Davis training windows) = HLA's unsupervised ML baselines on log patterns, surfacing deviations as alerts grouped by service/CI. Alert triage workflows port over: filter by impact, drill to raw logs (HLA express list equivalent to Dynatrace problems view). Bonus: Your Moogsoft/Datadog noise suppression skills apply to HLA alert grouping policies.

Q: Where does ServiceNow's approach fundamentally differ?

A: Dynatrace is runtime-centric (traces first, logs secondary); HLA is log-native with CMDB enforcement—logs must map to CIs/services during ingestion, or they orphan. No full-stack auto-discovery like Smartscape; relies on Service Mapping for topology. GenAI is table stakes now: Now Assist augments HLA anomalies with natural language root cause, but lacks Davis's causal chain probability scoring. Honest gap: HLA excels at platform self-healing (Glide logs analysis) but lags in app-layer synthetics without extra Event Management CI identifiers.

Q: How do I become the Dynatrace-ServiceNow bridge expert?

A: Activate HLA plugins (Health Log Analytics Core/Viewer), stream your first log source via guided setup, script a custom parser for Dynatrace-like field extraction. Build a CMDB bridge: map Dynatrace hosts to cmdb_ci_server via REST API sync. Cert path: Certified Implementation Specialist - ITOM + current-family HLA docs mastery. Production hack: Instrument MID Servers with HLA self-logging for meta-observability; demo cross-correlation of Dynatrace alerts into ServiceNow incidents.

Hands-On: See It Work

// Dynatrace-to-HLA Bridge: Custom Log Parser Script (HLA Data Collection phase)
// Equivalent: Dynatrace Custom Metric Events parser, but JS for ServiceNow log normalization
// Deploy as Parsing Script in HLA Integration setup
(function parseDynatraceLogs(payload) {
    // Input: raw log line from MID proxy stream (Dynatrace export)
    // Output: structured fields mapped to CI/Service for correlation
    var logLine = payload.log;
    var fields = {};
    
    // Extract like Dynatrace log viewer regex (e.g., ERROR level, host, service)
    var errorMatch = logLine.match(/ERROR\s+\[(\w+)]\s+(\w+):\s+(.*)/);
    if (errorMatch) {
        fields.level = 'ERROR';
        fields.host = errorMatch[1];      // Maps to cmdb_ci_server.name
        fields.service = errorMatch[2];   // Maps to cmdb_ci_service.name
        fields.message = errorMatch[3];
        
        // CMDB Lookup (your Davis entity bridge)
        var ciGR = new GlideRecord('cmdb_ci_server');
        if (ciGR.addQuery('name', fields.host).get()) {
            fields.ci_sys_id = ciGR.getUniqueValue();
        }
        
        // Service Mapping attachment
        var svcGR = new GlideRecord('cmdb_ci_service');
        if (svcGR.addQuery('name', fields.service).get()) {
            fields.service_sys_id = svcGR.getUniqueValue();
        }
        
        // Anomaly flags (HLA ML will baseline these)
        if (fields.message.includes('timeout') || fields.message.includes('OOM')) {
            fields.severity = 'CRITICAL';
            fields.anomaly_type = 'performance';
        }
    }
    
    // Normalize for HLA streaming (em_event compatible)
    payload.parsed = {
        source: 'dynatrace_bridge',
        node: fields.host,
        type: 'HLA_ANOMALY',
        resource: fields.ci_sys_id || 'UNKNOWN',
        description: fields.message,
        severity: fields.severity || 'INFO',
        additional_info: JSON.stringify(fields)
    };
    
    return payload.parsed;  // Feeds HLA ML engine
})(input);

This script runs during HLA ingestion: grabs Dynatrace-exported logs via MID proxy, extracts fields like your log viewer, queries CMDB live for topology (PurePath entity link), normalizes to em_event format. Deploy via HLA guided setup, stream logs, watch anomalies group in Express List with CI attachments. Production tweak: Add rate limiting for high-volume Dynatrace clusters; test with Glide logs first (no external source needed).

What Transfers vs What's Different

Transfers directly: Anomaly baselining, correlation rules, noise suppression, RCA workflows, ML interpretability. Your Datadog/New Relic log querying = HLA raw log triage; PagerDuty escalation = ServiceNow Incident routing from HLA alerts.

New learning curve: CMDB as topology enforcer—Dynatrace auto-discovers, ServiceNow demands clean CIs or orphans pile up. MID Server scaling (herd management) vs OneAgent self-healing. GenAI prompts over Davis scoring. Trade-off: HLA's platform self-analysis (Glide/MID logs) gives meta-insights Dynatrace skips, but requires the matching family plugins.

The Business Impact

HLA + your Dynatrace patterns collapse observability silos into intelligent operations: predictive incidents from log anomalies cut MTTR 40-60% by auto-correlating to business services, not just tech stacks. Orgs cut outage-response cost materially; automated RCA lifts SLA attainment. You deliver the bridge: unified AIOps where Dynatrace feeds ServiceNow incidents, turning tactical monitoring into strategic service health.

Common Traps to Avoid

  • Trap: Streaming unparsed Dynatrace logs without CI mapping—creates alert floods with no topology. Solution: Always script normalization phase; validate CMDB coverage >90% first.
  • Trap: Ignoring MID herd overload in scale-outs. Solution: One MID per 10k EPS; enable HLA self-logging for capacity alerts.
  • Trap: Treating HLA as "Dynatrace lite"—missing genAI capabilities. Solution: Pipe every anomaly to Now Assist for narrative RCA; beats Davis on human-readable summaries.
  • Trap: Skipping baseline warmup (24hr cold start). Solution: Pre-warm with historical logs; monitor integration dashboard for streaming rate.
