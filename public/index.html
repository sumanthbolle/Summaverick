Capabilities

Five kinds of work. Each one has a deliverable, not a workshop.

If you already know which of these you need, skip to it. If you do not, send the problem — we will tell you which of these it is, and which it is not.

Store apps

Develop, publish, and certify — on a timeline that holds.

Scoped ServiceNow applications, built on the Fluent SDK and taken through Store publishing and certification. Matched to the release you actually run, not the newest one on a slide. If certification is the bottleneck, that is the work we start with.

  • Certifiable scoped app and Store listing package
  • Release matrix for the instances in production
  • Publishing and certification support through Store approval

Implementation

Kickstart a ServiceNow programme with AI in the first sprint.

Most implementations bolt AI on in a later phase. We put Now Assist and the custom work next to process design, so the first go-live already has the skills and the guardrails. A diagnostic first, then a sprint that produces a running slice — not a deck.

  • Process and ticket-mix diagnostic
  • Now Assist skill plan: what to turn on, what to leave off
  • A working first slice on the instance you will live on

AI systems

A smarter AI implementation — on the platform you already have.

Licensed Now Assist that nobody uses. Agents that sound confident and cite nothing. We read the actual work, turn on the skills that pay off, and build custom agents only where the platform will not. Guardrails and evals are part of the build, not a later phase.

  • Skill and agent map against real ticket volume
  • Custom agents with a narrow tool surface and a verifier
  • Injection checks, citations, and an eval suite you can rerun

Product collaboration

Build a product on ServiceNow — or one that does a similar job.

Joint product work: a Store app, a companion system, or a platform that covers the same operational ground in a different stack. We build with you, not a body-shop bench. Intellectual property and the operating model are agreed before the first commit.

  • Shared product brief and ownership model
  • Working software on a release cadence you can keep
  • A team that can extend it after the engagement

Fine-tuning

Fine-tune at a cost that makes sense, or improve the AI you already run.

Domain fine-tuning and evaluation against your data, or better retrieval and tooling around the models already in the environment. The goal is a model you own, wired into the workflows that matter, without a blank-check GPU bill.

  • Fine-tune or retrieval plan with a cost envelope
  • Eval set from real tasks, not a public benchmark
  • Wiring into ServiceNow or the surrounding ecosystem

What this looks like in practice.

Client names are withheld. These are representative engagements — the constraints are the point.

Enterprise software vendor

GenAI platform on Bedrock, with a local fallback

Teams needed generative features without sending customer data to a single hosted model.

A retrieval and generation layer over Bedrock, with an Ollama path for workloads that had to stay on-prem. One interface; two backends chosen per data sensitivity.

Constraint held: routing is the client’s per workload. Model choice is config, not code.

Warranty operations

Multi-agent warranty automation

Claims triage was manual, and the rules changed often enough that a single prompt kept drifting.

Specialised agents for intake, policy lookup, and adjudication — each with a narrow tool surface and a verifier between them.

Constraint held: no agent approves a payout. Adjudication proposes; a person commits.

ServiceNow customer

Now Assist adoption

Now Assist was licensed and barely used. Nobody could say which skills were worth turning on.

Ticket mix read against the shipped skills, a short list of where the payoff was real, and a rollout in that order.

Constraint held: two skills stayed off — the data to justify them was not there yet.
