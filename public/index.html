Illustrative experience

The same idea, in two very different places.

A person needs something done. The agent brings the context together, proposes one concrete next step, and hands the decision back. Below are two walk-throughs built from sample data — pick a view and step through it.

Illustrative experience · sample data

On a phone: an unpaid refund

  1. Person

    Shared a screenshot

    Order 4821 · Returned 2 Sep Refund status: not issued

  2. Agent

    A refund for a returned order hasn't arrived. I can see the order number, but not the return reference — do you have it?

  3. Agent

    Draft follow-up

    “I returned order 4821 on 2 September and the refund hasn't reached my account. Could you confirm when it was issued?”

  4. Person decides

  5. Afterwards

    Follow-ups

    Refund · order 4821 — waiting for a reply, check back Friday

What each step is there to show

  1. Start from information the person already has.
  2. Say what is uncertain, and ask for it.
  3. Produce something concrete, not only a reply.
  4. Leave the decision with the person.
  5. Carry the task past the first answer.

At work: a service request that needs a decision

  1. Request

    REQ0010482 · Replacement laptop

    Raised by a new joiner in finance. Priority 3.

  2. Agent gathers context

    • Standard build applies to this role
    • Sample stock check: 6 available
    • Cost centre FIN-204, within the usual limit

  3. Agent proposes

    “Approve the standard build and ship to the Hyderabad office.”

    Reviewer: the requester's team manager

  4. Reviewer decides

  5. Afterwards

    Task history

    09:41 Agent proposed an update

    09:44 Manager accepted it

What each step is there to show

  1. A task the business already recognises.
  2. Context gathered inside the task, not around it.
  3. A proposal, and a named person to judge it.
  4. A controlled boundary: the reviewer acts, not the agent.
  5. A record of what changed, and when.

Both walk-throughs use invented data. Nothing here contacts a merchant, opens a ticket, or changes a record — pressing a button advances the illustration and nothing else.

What we build.

Every engagement ends in something you can use. We scope one job worth doing, design the agent and how people work with it, connect it to the right systems, and ship it—then help you keep it running.

Personal agents

A personal assistant built around one recurring job—chasing a refund, staying on top of follow-ups, tracking what needs attention. We shape its purpose, its conversation, and the context it's allowed to use.

Mobile experiences

A mobile app or agent made for the moment—share a screenshot, speak a request, approve a suggested action on the go. We handle the design, the build, and the on-device experience.

Enterprise agents

An agent inside the work your team already does, wired into ServiceNow or your own systems—with data access, guardrails, and review steps agreed up front. We build the integration and the workflow around it.

What this demo does

It searches the public ServiceNow product documentation, picks the pages that match the words in your question, and shows each one with an excerpt and a link. Results are ranked by keyword matching, so a listed page matched the question — reading the source is still how you confirm the answer.

It only covers ServiceNow. Written answers appear only where an answer model is enabled on the deployment, and the tool says which of the two you are looking at before you ask.

Why we build these products.

We started with an interest in the everyday tasks people struggle to get through. Our early hackathon concept explored an assistant for refunds, subscriptions, and follow-ups. That ambition shapes Summaverick today: developing agents for personal life and enterprise work, wherever people need to use them.
